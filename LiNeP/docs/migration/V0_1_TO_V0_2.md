# Migrating LiNeP V0.1 → V0.2

LiNeP V0.2 is not a wire-compatible extension of V0.1. It is an architectural evolution that preserves selected principles—especially the dual-plane split—while defining a broader, engine-neutral runtime interoperability contract.

## What carries forward

- UDP and TCP remain parallel control/data reference planes.
- Liveness and execution payload are separate concerns.
- Missing control traffic does not automatically prove that running TCP work stopped.
- Explicit state transitions and retry/idempotency rules remain central.

## What changes materially

V0.2 adds or formalizes concepts that MUST NOT be assumed in V0.1:

- transport-neutral runtime semantics;
- canonical runtime envelope families;
- persistent multiplexed TCP runtime sessions;
- full stream identity `(request_id, execution_id, output_id)`;
- logical `event_seq` ordering;
- explicit window/backpressure semantics;
- runtime profiles such as GENERATE, CHAT, and EMBED;
- embedding-space identity and metadata;
- control epoch/incarnation semantics;
- explicit lease-token binding between UDP control identity and TCP trunk/session;
- stronger failure/outcome semantics including `UNKNOWN`;
- cross-language conformance expectations.

## Migration rule

A V0.1 implementation MUST NOT be relabelled as V0.2 merely because it uses UDP + TCP. A V0.2 implementation must satisfy the V0.2 normative contract and conformance requirements.

Recommended migration sequence:

```text
1. Preserve V0.1 behavior as frozen baseline.
2. Introduce V0.2 framing and runtime identity separately.
3. Implement persistent TCP multiplexing and lifecycle semantics.
4. Implement V0.2 UDP epoch/lease/state-machine semantics.
5. Bind both planes explicitly.
6. Add runtime profiles and capabilities.
7. Pass V0.2 conformance and cross-language interoperability tests.
```

Adapters may support V0.1 and V0.2 side-by-side, but version negotiation/routing MUST keep their semantics isolated.

## Python package boundary

The Python distribution is versioned as `0.2.0` and exposes the V0.2 dual-plane
implementation while retaining an explicit `linep.v0_1` compatibility namespace.
This is a packaging/API evolution; it does not rewrite the frozen V0.1 C/C++ wire,
transport, C-ABI, or regression-test baseline. Applications that require V0.1
semantics should import or select that compatibility surface explicitly rather
than inferring protocol version from the top-level package version.
